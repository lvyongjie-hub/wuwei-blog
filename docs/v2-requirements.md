# 五味书房 V2 需求基线

- 目标版本：`v2.0.0`
- 基线版本：`v1.0.0`（提交 `bbdf6b5`）
- 开发分支：`feature/v2`
- 确认日期：2026-07-27
- 状态：范围已确认，待分阶段实现

## 1. 版本目标

V1 已完成网站结构、视觉系统和内容工具链。V2 的目标是让“五味书房”从完整骨架进入可持续公开发布阶段：用真实内容和可核查证据建立个人品牌，同时完善发现、阅读、联系与部署闭环。

V2 不改变以下长期定位：

- 核心身份仍是嵌入式系统与固件工程。
- 边缘 AI、TinyML 和端侧模型仍是与工程实践相连的第二专业支柱。
- 主要面向技术同行、潜在合作伙伴和少量招聘者。
- 中文为主，关键项目和代表文章补充英文标题、摘要与技术关键词。
- 不虚构项目、文章、实验数据、硬件照片或验证结论。

## 2. 发布原则

- 不增加一级导航，继续使用“书房 / 项目档案 / 随笔 / 关于”。
- 实验记录继续作为独立内容类型出现在首页和书房相关入口，不提升为一级导航。
- 内容仍由 Markdown/MDX 与 Git 管理；在线后台只是 Git 内容编辑入口，不引入数据库。
- 首页内容从 Content Collections 自动生成，避免在页面中重复维护文章信息。
- 没有真实内容时继续显示诚实的空状态，不使用演示数据填充。
- 代码功能完成与内容发布可以分开验收；公开内容必须有可确认的真实素材。

## 3. V2 范围

### 3.1 内容首发

V2 正式发布至少包含：

- 一篇工程深度文章，主题属于 MCU、RTOS、驱动协议、系统可靠性或真实问题排查。
- 一篇嵌入式 × AI 实验记录，必须包含目标、环境、步骤、观察、限制和可复现信息。
- 对 STM32F407 四通道工业数据记录终端项目档案进行一次证据化更新。

内容素材由五味确认后录入。缺少真实数据、图片或硬件观察时，应明确标注“待验证”“仅静态验证”或“代码未公开”，不得补造结果。

### 3.2 首页内容化

- “代表文章”改为从真实书房文章中读取精选内容。
- “当前研究方向”能够呈现最新实验与真实的此刻状态。
- “最近随笔”继续自动读取已发布随笔。
- 首页各区块在有内容和无内容时都保持稳定布局。
- 精选规则由 frontmatter 控制，不在首页硬编码文章标题或链接。

### 3.3 内容模型升级

- 为代表文章和关键项目增加明确的精选字段。
- 关键内容支持英文摘要和英文技术关键词。
- 支持内容之间的显式关联：项目、实验、知识库文章可以互相引用。
- 支持可选修订记录，用于说明重要内容变更及适用版本变化。
- 继续保留首次发布日期、最后更新时间、适用平台与内容生命周期信息。
- 构建阶段校验精选内容的关键双语元数据，避免不完整内容进入正式发布。

### 3.4 项目证据与档案增强

- 项目页支持真实硬件照片、界面截图、波形、架构图或测试记录组成的证据区。
- 每项证据包含替代文本、说明、证据类型和验证状态。
- 区分“设计说明”“编译/静态验证”“主机测试”“板级测试”和“长期运行测试”。
- 项目页展示相关实验、相关文章和知识库章节。
- 支持简短修订时间线，记录项目状态和公开边界的变化。
- 没有公开仓库或演示时继续明确显示“仅展示案例”或“代码未公开”。

### 3.5 阅读与发现体验

- 文章页增加同主题相关内容入口。
- 标题锚点支持复制永久链接，并保持无 JavaScript 时正文可读。
- 桌面目录和移动目录继续保持现有三栏/抽屉模式，并完善当前章节反馈。
- 搜索继续覆盖项目、书房、实验和随笔，支持英文摘要与技术关键词。
- 保留 RSS，并确保新增公开内容能够进入订阅源。
- 不在 V2 引入访客阅读进度、点赞、账号或复杂社交功能。

### 3.6 品牌、联系与可信度

- 使用最终确认的专用联系邮箱。
- 关于页补充经五味确认的匿名化经历时间线。
- 继续以“五味”作为页面署名和公开元数据作者，不公开真实姓名。
- 完善“书票式五味印记”的细节，但保持克制的现代编辑风格。
- 关键项目和代表文章的社交预览图展示英文标题或技术关键词。

### 3.7 SEO 与结构化信息

- 为网站和作者增加合适的 JSON-LD；作者只使用公开身份“五味”。
- 项目、工程文章和实验记录使用与内容类型匹配的结构化数据。
- 校验 canonical、Open Graph、RSS、Sitemap 和 robots 配置与最终站点地址一致。
- 不在公开元数据中写入真实姓名、私人邮箱或未确认经历。

### 3.8 互动与部署

- GitHub Discussions 配置完成后启用 Giscus；未配置时保持当前占位状态。
- 配置 Cloudflare Workers：`main` 为正式站点，Pull Request/功能分支生成预览部署。
- 配置 Cloudflare Web Analytics 时只使用无广告追踪的基础统计。
- 最终域名未确定前可以先使用 `workers.dev` 地址完成部署验收。
- 环境变量和平台 ID 只保存在 GitHub/Cloudflare 配置中，不写入仓库。

### 3.9 Git 内容后台

- 提供不进入一级导航的 `/admin/` 内容后台。
- 使用开源 Sveltia CMS 管理书房文章、实验、随笔、项目档案和知识库目录。
- 后台继续读写仓库内 Markdown/MDX 和图片，不建立独立数据库。
- 线上后台仅允许 GitHub 细粒度 access token 登录，令牌不写入仓库或前端配置；本地开发可以通过浏览器文件系统授权直接编辑博客仓库。
- access token 只允许访问 `wuwei-blog` 仓库，并只授予 Contents 读写权限。
- Sveltia CMS 尚不支持 Editorial Workflow；后台保存直接提交到 `main`，由 CI 和 Cloudflare 构建保护正式站点。
- 后台禁用删除入口；撤下内容优先使用草稿或归档状态，真正删除仍通过本地分支和 PR 完成。
- 后台为每种内容类型管理一种规范扩展名；包含 Astro 组件或复杂结构的高级 MDX 继续通过本地编辑器维护，不承诺出现在后台列表中。
- 私人草稿和敏感资料不得进入公开仓库，`draft: true` 不是隐私措施。
- 后续如需更友好的 GitHub OAuth 登录，再部署 Sveltia 官方 Cloudflare Worker 认证服务。

## 4. 明确不做

V2 不包含：

- 新增一级导航或重构现有信息架构。
- 全文中英双语。
- Newsletter、邮件订阅或营销自动化。
- 独立数据库、用户注册、多角色权限系统和自建账号体系。
- PWA、离线缓存和原生应用封装。
- 点赞、打赏、付费内容或复杂评论社区。
- 大型真人首页照片、重拟物书架或木桌界面。
- 为填满页面而制作虚构文章、实验结果或 AI 硬件照片。

## 5. 外部输入与依赖

以下信息缺失时，不阻塞通用组件开发，但会阻塞对应内容或正式上线：

- 专用联系邮箱。
- 匿名化职业经历时间线。
- 首篇工程文章的真实素材。
- 首篇嵌入式 × AI 实验的环境、步骤和结果。
- STM32F407 项目的真实照片、截图、波形或测试记录。
- Giscus 的仓库、仓库 ID 和分类 ID。
- Cloudflare Workers 项目与 Web Analytics token。
- 最终域名及其 DNS 控制权。

## 6. 实施阶段

### 阶段 A：内容基础设施

- 升级内容 schema、模板和构建校验。
- 实现精选内容、双语元数据、关联内容和修订记录。
- 实现项目证据区、结构化数据和首页动态内容。
- 接入 Git 内容后台，并完成所有内容类型的字段映射。
- 在无新增真实内容的情况下完成回归验证。

### 阶段 B：真实内容接入

- 录入并审校首篇工程深度文章。
- 录入并审校首篇嵌入式 × AI 实验。
- 使用真实材料增强 STM32F407 项目档案。
- 补充关于页时间线和专用邮箱。

### 阶段 C：预览与发布

- 配置 Giscus、Cloudflare Workers 和可选 Analytics。
- 在 Cloudflare 预览环境完成桌面、移动、明暗主题和社交预览检查。
- 完成发布前自动检查与人工浏览器验收。
- 合并至 `main`，发布并标记 `v2.0.0`。

## 7. 验收条件

V2 只有同时满足以下条件才可正式发布：

- 首页能够自动展示真实精选文章、最新实验和项目内容。
- 至少一篇代表文章具有英文标题、英文摘要和英文技术关键词。
- 至少一篇嵌入式 × AI 实验记录包含真实且可复现的工程信息。
- STM32F407 项目档案至少增加一项真实证据，且验证状态描述准确。
- 项目、文章和实验之间的关联入口可用，不产生失效链接。
- 关于页只包含经确认的匿名化经历和公开联系方式。
- JSON-LD、Open Graph、canonical、RSS、Sitemap 与正式地址一致。
- Giscus 和 Analytics 在缺少配置时安全降级，在配置后正常工作。
- `/admin/` 能通过 GitHub 细粒度 access token 登录并管理所有公开内容类型。
- 后台页面不进入 Sitemap，且具有 `noindex` 响应头和 robots 规则。
- 后台不包含仓库令牌、OAuth Secret 或其他凭据。
- `npm run verify` 全部通过。
- 主流桌面和移动尺寸下完成明暗主题、导航、搜索、目录和内容页检查。
- Lighthouse 的 Performance、Accessibility、Best Practices 和 SEO 以 90+ 为目标；未达到时记录原因和处理结论。
- 未执行的板级测试、测量和长期运行测试没有被描述为已通过。

## 8. 变更控制

V2 开发中的新增需求应记录：

- 变更内容与原因。
- 是否影响既定导航、内容模型或隐私边界。
- 是否需要新的用户素材或平台权限。
- 对发布时间、验证范围和兼容性的影响。

未经明确确认，不把“明确不做”中的项目自行加入 V2。

## 9. 已确认范围变更

### 2026-07-27：增加 Git 内容后台

- 变更原因：降低新增文章和项目档案时直接操作文件与 Git 命令的门槛。
- 替代决定：V2 原定“不做在线 CMS”调整为“提供无数据库的 Git 内容后台”。
- 技术影响：增加仅后台页面加载的 Sveltia CMS 前端包、后台字段配置和访问令牌操作说明；公开网站仍为 Astro 静态输出。
- 发布影响：后台内容保存会直接提交到 `main`，因此必须保留 CI 和 Cloudflare 构建检查，不允许后台写入代码、工作流或环境配置。
- 隐私影响：后台草稿仍位于公开 Git 仓库，不得用于保存私人内容或敏感工程资料。

### 2026-07-27：精简下一开发迭代

- 下一迭代只增加书房文章 `featured` 字段、首页代表文章和最新实验的自动展示，并同步后台配置。
- 代表文章按“精选优先、发布日期倒序”展示；没有内容时继续保留空状态。
- 关联内容、修订历史、结构化证据、复杂 JSON-LD、Giscus、Analytics 和 OAuth 延后处理。
- 项目证据暂时直接通过正文中的图片与文字表达，不建立新的结构化证据模型。
